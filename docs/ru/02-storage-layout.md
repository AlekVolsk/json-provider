# Раскладка на диске

Хранилище — это один каталог:

```text
db/
├── .locks/                     # файлы блокировок (см. «Конкурентность»)
│   ├── db.lock
│   ├── table.users.lock
│   └── svc.meta.json.lock
├── information_schema.json     # таблицы, индексы, связи
├── meta.json                   # счётчики таблиц (lastInsertedId, lineCount, byteSize)
├── users/
│   ├── users.ndjson            # данные таблицы, одна запись на строку
│   ├── pk.index.ndjson         # обязательный индекс первичного ключа
│   └── idx_users_email.index.ndjson
└── boards/
    ├── boards.ndjson
    ├── pk.index.ndjson
    └── ...
```

Конвенции (обеспечиваются провайдером):

- одна таблица — один подкаталог, имя совпадает с именем таблицы;
- файл данных — `<table-name>.ndjson`;
- файл индекса — `<index-name>.index.ndjson`;
- все имена на диске — каталог таблицы, файлы данных и индексов, лок-файлы, члены архива бэкапа — **в нижнем регистре**, в схеме имена хранятся как заданы: таблица `Orders` с индексом `byDate` лежит в `orders/orders.ndjson` и `orders/bydate.index.ndjson`. Раскладка поэтому одинакова на регистрозависимых и регистронезависимых ФС, а имена, различающиеся только регистром, заняли бы одни файлы и считаются одинаковыми (см. [модель схемы](04-schema-model.md#имена-таблиц-колонок-и-индексов));
- PK-индекс называется `pk` и присутствует всегда;
- `.locks/` — служебный dot-каталог с постоянными пустыми файлами блокировок; в бэкап и валидацию не входит, удалять его не нужно (и не нужно бэкапить);
- `*.tmp` рядом с файлами данных — временные файлы атомарной записи (tmp + fsync + rename); сирота от упавшего процесса вычищается следующей записью того же файла.

Не нужно добавлять или удалять файлы внутри каталога вручную — валидатор целостности отметит их как orphan-ы, а репэйрер вычистит.
