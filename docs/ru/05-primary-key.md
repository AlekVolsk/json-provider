# Контракт первичного ключа

У каждой таблицы есть PK. Это **не** настройка — это инвариант провайдера:

- колонка называется `id`,
- тип — `int`,
- всегда первая колонка в `columns`,
- автоинкремент (id выдаёт провайдер),
- id никогда не переиспользуются после удаления (дырки — норма); id, выделенный упавшей вставкой до фиксации записи, тоже сгорает — это штатная дырка. Единственное исключение — восстановление потерянной меты (самолечение, `repair`, `restore`): счётчик восстанавливается как `max(id)` живых записей, поэтому id удалённых «верхних» строк могут выдаться повторно,
- в таблице всегда есть PK-индекс с именем `pk` на нулевой позиции.

Константы — в `Schema\PrimaryKey`:

```php
PrimaryKey::FIELD;  // 'id'
PrimaryKey::TYPE;   // 'int'
```

Нарушение контракта (испорченная схема при чтении, прямой `new TableSchema(...)` с ошибками, регистрация некорректной схемы) → `StorageException` с ключом `PK_CONTRACT_VIOLATED`.

Фабрика `TableSchema::create(...)` сглаживает пользовательские неточности: дописывает отсутствующий `id`, перемещает `id` в начало, дописывает PK-индекс. Что она **не** прощает — неправильный **тип** для `id`. Это семантическая ошибка, всегда исключение.

## Защита от отката счётчика

Вставки выделяют монотонно растущие id, поэтому файл данных упорядочен по id. Перед выделением id `insert` за O(1) сверяет id последней строки файла со счётчиком меты: если счётчик отстал (в `meta.json` подложили бэкап, правили руками), следующая вставка отчеканила бы дубликат PK. В этом случае watermark сначала восстанавливается из данных (`max(id)`), под тем же EX-локом, и только затем выделяется id.

Уже хранящийся дубликат PK — находка валидатора `pk_duplicate` (error, с id и номерами строк в контексте). `repair()` его **не** чинит автоматически: движку неоткуда знать, какая из строк авторитетна, — решение ручное.
