# Модель конкурентности

Провайдер использует трёхуровневую иерархию межпроцессных блокировок (flock на постоянных пустых файлах в служебном каталоге `db/.locks/`):

1. **База** — `db.lock`. SH берёт любая DML-запись (insert/update/delete); EX — DDL (createTable, dropTable, migrateColumns, reorderColumns), restore, backup и repair всей БД.
2. **Таблицы** — `table.<имя>.lock`. EX для записываемых таблиц, SH для таблиц, которые в критической секции только читаются (restrict-дети). Захват строго по возрастанию имени.
3. **Служебные файлы** — `svc.<имя>.lock`, короткие «листовые» сайдкары для `meta.json` и `information_schema.json`. Берутся последними и не компонуются: держа лист, нельзя брать локи уровней 1–2.

Порядок захвата тотальный: база → таблицы по имени → листы. Повышение режима (SH→EX) и захват вне порядка запрещены и дают `JsonProviderLockException`. Ожидание ограничено 30 секундами, дальше `JsonProviderLockException`. Локи живут вместе с процессом: упавший держатель ничего не оставляет заблокированным.

Набор таблиц для записи вычисляется по графу связей схемы. `insert` берёт EX только на свою таблицу. `delete` — EX на свою таблицу и по действиям `onDelete`: `cascade`- и `setNull`-дети EX, `restrict`-дети SH; удалённые каскадом дети продолжают по своим `onDelete`, а обнулённые — по своим `onUpdate`, потому что обнуление — это изменение значения. `update` идёт только по действиям `onUpdate`: у связей на `id` их нет, поэтому `update` такой таблицы блокирует только её саму, а не дерево потомков. Родители не блокируются никогда: ни одно FK-действие не читает строку родителя, а удаление родителя или изменение его ключа блокирует дочернюю таблицу и поэтому упорядочивается со вставкой в неё. Циклы графа безопасны. Если движок обращается к таблице, которой нет в захваченном наборе, это `JsonProviderLockException` с кейсом `LockOrderTableOutsideHeldSet`, а не гонка.

## Чтения

Двухуровневая модель:

- **Full scan (лок-фри).** Полное чтение файла данных не берёт никаких блокировок. Корректность обеспечивается атомарной заменой файла при перезаписи (tmp + fsync + rename): читатель всегда видит целостный старый либо целостный новый файл. Снимок соответствует моменту открытия файла — insert-ы, завершившиеся позже, в него могут не попасть.
- **Индексные выборки (снимок под блокировкой).** Под SH-локом таблицы выборка через индекс проверяет доверие к индексу и открывает файлы: файл данных и отсортированную голову файла индекса. Хвост индекса читается в память; весь файл индекса читается в память, когда голова не записана или выборка идёт в порядке индекса без условий. Затем лок отпускается, и поиск по голове и чтение строк идут из открытых файлов в пределах размера файла данных на момент снимка. Писатель переписывает таблицу в новые файлы (tmp + fsync + rename) или дописывает строки в конец; байты открытых файлов в пределах снимка не меняет ни одна версия, поэтому пара «индекс + данные» согласована, и ответ даёт версия на момент снимка. Смещения строк берутся, только если производный файл описывает именно открытый файл данных; иначе строки читаются одним проходом по нему.

Full-scan `select()` и `count()` полным просмотром или из счётчика меты — лок-фри; `count()` через индекс берёт снимок под SH-локом таблицы, как индексная выборка.

## Записи

Каждая запись — read-modify-write строго от диска: базой перезаписи никогда не служит кэш. Полная перезапись файла идёт через буферизацию (некодируемая запись отбивает операцию целиком, файл не тронут), затем tmp + fsync + rename. Append дописывает с fsync и откатывает недозапись усечением — рваная строка никогда не подтверждается.

Первым шагом каждой записи работает O(1)-гейт консистентности: сверка `meta.byteSize` с фактическим размером файла, а в базе поколения 2 — ещё и inode файла со штампом `dataIno` в мете. Штамп ловит перезапись, оборвавшуюся между переименованием файла и коммитом счётчиков, даже когда размер совпал (см. [формат хранения](23-storage-format.md)). Расхождение (краш, внешняя правка) чинится самой операцией — канонической перезаписью таблицы с пересборкой индексов и коммитом фактических счётчиков. Это же штатный рецепт выхода из краша многотабличной записи: таблицы с рассинхроном дочиняются при следующей записи (или явным `repairTable()`); согласованность между таблицами после такого краша проверяет `validate()` — см. [мутации](10-mutations.md#как-исполняются-fk-действия).

## Кэш

Кэш-слой — только для чтений; ключи версионированы состоянием таблицы (см. [кеширование](16-caching.md)): тег ключа складывается из счётчика строк меты, физического размера файла данных и его inode, поэтому любая зафиксированная мутация — своя, чужого процесса или даже прямая правка файла, меняющая его размер, — просто выводит устаревшие записи кэша из оборота без инвалидационных сообщений; inode (новый при каждой tmp+rename-перезаписи) исключает и A-B-A-совпадения тега (delete+insert той же длины, truncate с реимпортом, замена значения той же длины через провайдер). Лок-фри читатель при промахе заполняет кэш оптимистично, без локов: конкурирующая запись может лишь положить под старый тег БОЛЕЕ СВЕЖИЙ снапшот, к которому после коммита писателя уже никто не резолвится, — «путешествие в прошлое» исключено по построению. Мутации публикуют свежий снапшот под тегом только что зафиксированного состояния внутри своей EX-секции. Остаточное окно — чужая правка файла **на месте** без изменения размера (in-place, без rename); ручной выход — `$db->invalidateCache($tableName)`.

## Ограничения

- POSIX-only: flock по сетевым ФС (NFS) и Windows не поддерживаются, см. [требования](20-requirements-dependencies.md).
- Дескрипторы локов наследуются дочерними процессами: долгоживущий ребёнок, запущенный из критической секции (proc_open, exec), удерживает лок до своего завершения. Не запускайте долгоживущих детей под локами.
- Блокировку процесс ждёт неблокирующим flock с ретраями раз в 2 мс; очереди на уровне ОС нет. Чтобы поток перекрывающихся SH-читателей не голодоморил EX-писателя, у блокировок базы и таблиц есть турникет — файл `gate.<файл блокировки>` в `.locks/`. Писатель держит его, пока ждёт свою блокировку, а читатель проходит через него перед своей, поэтому читатели, пришедшие после писателя, ждут за ним. У листовых блокировок турникета нет: их держат коротко.
- Межфайловая транзакционность (несколько таблиц одним атомом) не предоставляется; см. рецепт самовосстановления выше.
- Версии 1.0, 1.1 и 1.2 берут одни и те же файлы блокировок в одном порядке, поэтому при выкладке старые и новые процессы могут работать одновременно (см. [откат и смешанная выкладка](07-migrations.md#откат-и-смешанная-выкладка)). Турникет берёт только 1.2: читатели 1.1 и 1.0 за ждущим писателем не встают и держат SH-лок на всё время индексного чтения. Писатель сборки, не берущей блокировок, с ними не взаимоисключается — такие процессы нужно остановить до обновления.
- Манифест формата хранения читается один раз на экземпляр провайдера: долгоживущий процесс видит миграцию формата, выполненную другим процессом, только после перезапуска.
