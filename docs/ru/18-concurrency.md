# Модель конкурентности

Провайдер использует трёхуровневую иерархию межпроцессных блокировок (flock на постоянных пустых файлах в служебном каталоге `db/.locks/`):

1. **База** — `db.lock`. SH берёт любая DML-запись (insert/update/delete); EX — DDL (createTable, dropTable, migrateColumns, reorderColumns), restore, backup и repair всей БД.
2. **Таблицы** — `table.<имя>.lock`. EX для записываемых таблиц, SH для таблиц, которые в критической секции только читаются (родители по FK, restrict-дети). Захват строго по возрастанию имени.
3. **Служебные файлы** — `svc.<имя>.lock`, короткие «листовые» сайдкары для `meta.json` и `information_schema.json`. Берутся последними и не компонуются: держа лист, нельзя брать локи уровней 1–2.

Порядок захвата тотальный: база → таблицы по имени → листы. Повышение режима (SH→EX) и захват вне порядка запрещены и дают `LOCK_ORDER_VIOLATION`. Ожидание ограничено 30 секундами, дальше `LOCK_TIMEOUT`. Локи живут вместе с процессом: упавший держатель ничего не оставляет заблокированным.

Набор таблиц для записи вычисляется по графу связей схемы: мутируемая таблица EX, транзитивно все CASCADE/SET_NULL-дети EX, RESTRICT-дети SH, родители enforced-связей SH. Циклы графа безопасны.

## Чтения

Двухуровневая модель:

- **Full scan (лок-фри).** Полное чтение файла данных не берёт никаких блокировок. Корректность обеспечивается атомарной заменой файла при перезаписи (tmp + fsync + rename): читатель всегда видит целостный старый либо целостный новый файл. Снимок соответствует моменту открытия файла — insert-ы, завершившиеся позже, в него могут не попасть.
- **Индексные выборки (координированные).** Выборка через индекс держит SH-лок таблицы на время чтения индекса и строк данных, поэтому писатель не может подменить файлы между чтением индекса и чтением строк — пара «индекс + данные» всегда согласована. SH-секция покрывает только I/O и отпускается до декодирования результата.

`count()` и full-scan `select()` — лок-фри.

## Записи

Каждая запись — read-modify-write строго от диска: базой перезаписи никогда не служит кэш. Полная перезапись файла идёт через буферизацию (некодируемая запись отбивает операцию целиком, файл не тронут), затем tmp + fsync + rename. Append дописывает с fsync и откатывает недозапись усечением — рваная строка никогда не подтверждается.

Первым шагом каждой записи работает O(1)-гейт консистентности: сверка `meta.byteSize` с фактическим размером файла. Расхождение (краш, внешняя правка) чинится самой операцией — канонической перезаписью таблицы с пересборкой индексов и коммитом фактических счётчиков. Это же штатный рецепт выхода из краша многотабличной записи: таблицы с рассинхроном дочиняются при следующей записи (или явным `repairTable()`).

## Кэш

Кэш-слой — только для чтений, по модели «invalidate on write»: DML через провайдер чистит кэш-запись затронутой таблицы; мутации кладут свежий снапшот в кэш только внутри своей EX-секции после публикации файла. Лок-фри читатель при промахе тоже заполняет кэш (оптимистично, без локов) — из-за этого существует узкое окно, в котором только что инвалидированная запись пере-заполняется снапшотом, прочитанным до мутации; оно живёт до следующей мутации таблицы. Для разделяемых адаптеров (Redis, Memcached) полная межпроцессная когерентность закрывается версионным тегом кэша (стадия «cache-coherence-version-tag» плана правок). При изменении хранилища в обход провайдера (или из другого процесса при in-memory-адаптере) вызовите `$db->invalidateCache($tableName)`.

## Ограничения

- POSIX-only: flock по сетевым ФС (NFS) и Windows не поддерживаются, см. [требования](20-requirements-dependencies.md).
- Дескрипторы локов наследуются дочерними процессами: долгоживущий ребёнок, запущенный из критической секции (proc_open, exec), удерживает лок до своего завершения. Не запускайте долгоживущих детей под локами.
- Очереди ожидания нет (неблокирующий flock с ретраями): непрерывный поток коротких SH-читателей теоретически способен голодоморить EX-писателя вплоть до `LOCK_TIMEOUT` под высокой нагрузкой. Провайдер рассчитан на умеренную конкуренцию.
- Межфайловая транзакционность (несколько таблиц одним атомом) не предоставляется; см. рецепт самовосстановления выше.
- Обновление библиотеки на работающем проде — только со стопом всех пишущих процессов: писатель старой версии (без локов) и писатель новой версии не взаимоисключаются.
