# Мутации — insert / update / delete

## Insert

```php
$id = $db->table('products')->insertByArray([
    'name'  => 'Widget',
    'price' => 9.99,
]);   // int — присвоенный id
```

`id` выдаётся провайдером (`lastInsertedId + 1`) и **не переиспользуется** после удаления. Поля, не объявленные в схеме, молча отбрасываются. Пропущенная в payload-е nullable-колонка становится `null`; пропущенная non-nullable — ошибка `RequiredColumnMissing` (полный контракт значений — в [Модели схемы](04-schema-model.md)).

Unique-ограничения проверяются перед записью. Нарушение → `JsonProviderDataException` с кейсом `UniqueViolation`.

## Update

DML-методы возвращают `bool`. `true` означает «операция отработала» — пустое множество совпадений — **не** ошибка.

Массовое обновление по условию:

```php
$ok = $db->table('products')
    ->where('categoryId', '=', $cat)
    ->where('active', '=', true)
    ->updateByArray(['price' => 0, 'active' => false]);
```

Обновление одной записи по id:

```php
$ok = $db->table('products')->updateByIdByArray($id, ['price' => 9.99]);
```

Поле `id` в payload-е update-а молча игнорируется — изменить его нельзя.

Число затронутых строк билдер помнит в `affectedRows()` — см. [ниже](#affected-rows).

## Delete

```php
$db->table('products')->where('discontinued', '=', true)->delete();
$db->table('products')->deleteById($id);
```

Foreign-key-действия (`cascade`, `setNull`, `restrict`) срабатывают автоматически по схеме. `restrict` бросает `ForeignKeyRestrict`, если есть дочерние записи, ссылающиеся на удаляемую.

## Как исполняются FK-действия

Весь многотабличный эффект delete/update просчитывается **до первой записи на диск** (фаза плана), затем применяется двухфазно:

- **План.** Движок обходит граф связей в ширину от затронутых строк корня, читая каждую затронутую таблицу с диска ровно один раз. Здесь же выполняется вся валидация: семантика исполняемых рёбер (колонки/типы — `RelationColumnNotFound`/`RelationTypeMismatch`), nullable-гарантия setNull (`ForeignKeySetNullNotNullable`), restrict-пробы по backing-индексу, типизация каскадных патчей тем же кодеком, что insert/update, и unique-проверки **финального** состояния batch-а (два target-а, схлопывающиеся в один unique-ключ, ловятся до записи). Любая ошибка плана оставляет диск нетронутым.
- **Каскады и циклы.** Строка, уже собранная к удалению, повторно не раскрывается — циклы A↔B и самоссылочные цепочки терминируются и удаляются целиком (транзитивные потомки не «воскресают»).
- **Restrict — MySQL-immediate.** Проба идёт по ИСХОДНОМУ состоянию ребёнка: нарушение считается, даже если сам ссылающийся ребёнок удаляется этим же запросом. Самоссылочную restrict-таблицу нельзя очистить одним delete-all — удаляйте листья→корни.
- **Применение (PREPARE/COMMIT).** Сначала каждая таблица плана кодируется и записывается во временный файл с fsync (любой сбой — например, незакодируемая строка — откатывает весь набор, файлы данных не тронуты), затем файлы переключаются rename-ами **дети-раньше-родителя**, после чего на таблицу пересобираются индексы, коммитятся счётчики меты и обновляется кэш. Краш между rename-ами оставляет каждую таблицу по отдельности целой (старый или новый полный файл); повторный запуск того же запроса сходится — благодаря порядку «дети первыми» уже удалённые дети не превращаются в невидимых сирот.

`onUpdate`-каскады работают только для связей на не-PK уникальную колонку (см. [связи](04-schema-model.md)) и распространяются транзитивно: обновление FK-колонки ребёнка, на которую ссылаются внуки, продолжает замыкание. Это касается и `setNull` при **delete**: обнуление FK-колонки ребёнка — это изменение значения, которое видят onUpdate-рёбра внуков — restrict-внук заблокирует удаление, cascade/setNull-внуки последуют за null.

## Массовая загрузка

```php
$written = $db->importRecords('products', $rows);   // int — сколько записано
```

Заменяет всё содержимое таблицы за одну перезапись — массовый аналог `insert()` для посева, импорта и восстановления. Каждая запись проходит ту же нормализацию и валидацию, что и при `insert()`, затем файл данных атомарно подменяется, индексы пересобираются, счётчики меты (`lineCount`/`byteSize`) фиксируются, а кэш публикуется заново. Итоговое состояние таблицы неотличимо от того, что оставила бы серия `insert()`, но обходится в разы дешевле.

`id` обязателен для каждой записи и должен быть уникален внутри партии: это загрузка известных записей, а не последовательность добавлений. Нарушения → `RecordImportIdInvalid` и `RecordImportIdDuplicate`. Автоинкремент выставляется по максимальному переданному `id`, поэтому следующий `insert()` продолжит нумерацию за импортированными строками.

Валидация проходит целиком до первой записи на диск: плохая строка в середине партии прерывает импорт, оставив таблицу нетронутой, а не наполовину заменённой.

Foreign-key-действия **не** проверяются (симметрично `truncate` и `dropTable`): импортируйте сначала родительскую сторону либо прогоните `validate()`, если источник данных не доверенный.

## Truncate

```php
$db->truncate('audit_log');
```

Семантика SQL `TRUNCATE`: все записи удаляются, индексы пересобираются пустыми, автоинкремент сбрасывается в 0 — следующая вставка получит `id = 1` (delete-all, в отличие от truncate, счётчик сохраняет). Foreign-key-действия **не** проверяются (симметрично `dropTable`): висячие FK-значения в детях остаются — если это важно, сначала обработайте детей. Неизвестная таблица → `TableNotFound`.

## Переименования

Смена имени колонки (`renameColumn`) и таблицы (`renameTable`) — DDL-операции, описаны в [Изменении схемы](12-schema-mutations.md): обе переносят данные, индексы, связи и мету на новое имя и защищены от крашей (для `renameTable` — маркером `_pendingRename`, который дочиняет `repair()`).

## Affected rows

```php
$tbl = $db->table('products');
$tbl->where('discontinued', '=', true)->delete();
echo $tbl->affectedRows();   // число строк последней DML
```

`affectedRows()` равен `0` до первой DML на этом билдере, дальше держит результат последней DML до следующей: чтение счётчика его не сбрасывает, read-операции (`select*`, `count`, `exists`, identifier-API) не меняют.
