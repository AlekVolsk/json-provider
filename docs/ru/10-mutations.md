# Мутации — insert / update / delete

## Insert

```php
$id = $db->table('products')->insertByArray([
    'name'  => 'Widget',
    'price' => 9.99,
]);   // int — присвоенный id
```

`id` выдаётся провайдером (`lastInsertedId + 1`) и **не переиспользуется** после удаления. Поля, не объявленные в схеме, молча отбрасываются. Поля схемы, отсутствующие в payload, становятся `null`.

Unique-ограничения проверяются перед записью. Нарушение → `StorageException` с ключом `UNIQUE_VIOLATION`.

## Update

DML-методы возвращают `bool`. `true` означает «операция отработала» — пустое множество совпадений — **не** ошибка.

Массовое обновление по условию:

```php
$ok = $db->table('products')
    ->where('categoryId', '=', $cat)
    ->where('active', '=', true)
    ->updateByArray(['price' => 0, 'active' => false]);
```

Обновление одной записи по id:

```php
$ok = $db->table('products')->updateByIdByArray($id, ['price' => 9.99]);
```

Поле `id` в payload-е update-а молча игнорируется — изменить его нельзя.

После update-а билдер помнит число затронутых строк до одного чтения через `affectedRows()`.

## Delete

```php
$db->table('products')->where('discontinued', '=', true)->delete();
$db->table('products')->deleteById($id);
```

Foreign-key-действия (`cascade`, `setNull`, `restrict`) срабатывают автоматически по схеме. `restrict` бросает `FOREIGN_KEY_RESTRICT`, если есть дочерние записи, ссылающиеся на удаляемую.

## Как исполняются FK-действия

Весь многотабличный эффект delete/update просчитывается **до первой записи на диск** (фаза плана), затем применяется двухфазно:

- **План.** Движок обходит граф связей в ширину от затронутых строк корня, читая каждую затронутую таблицу с диска ровно один раз. Здесь же выполняется вся валидация: семантика исполняемых рёбер (колонки/типы — `RELATION_COLUMN_NOT_FOUND`/`RELATION_TYPE_MISMATCH`), nullable-гарантия setNull (`FOREIGN_KEY_SET_NULL_NOT_NULLABLE`), restrict-пробы по backing-индексу, типизация каскадных патчей тем же кодеком, что insert/update, и unique-проверки **финального** состояния batch-а (два target-а, схлопывающиеся в один unique-ключ, ловятся до записи). Любая ошибка плана оставляет диск нетронутым.
- **Каскады и циклы.** Строка, уже собранная к удалению, повторно не раскрывается — циклы A↔B и самоссылочные цепочки терминируются и удаляются целиком (транзитивные потомки не «воскресают»).
- **Restrict — MySQL-immediate.** Проба идёт по ИСХОДНОМУ состоянию ребёнка: нарушение считается, даже если сам ссылающийся ребёнок удаляется этим же запросом. Самоссылочную restrict-таблицу нельзя очистить одним delete-all — удаляйте листья→корни.
- **Применение (PREPARE/COMMIT).** Сначала каждая таблица плана кодируется и записывается во временный файл с fsync (любой сбой — например, незакодируемая строка — откатывает весь набор, файлы данных не тронуты), затем файлы переключаются rename-ами **дети-раньше-родителя**, после чего на таблицу пересобираются индексы, коммитятся счётчики меты и обновляется кэш. Краш между rename-ами оставляет каждую таблицу по отдельности целой (старый или новый полный файл); повторный запуск того же запроса сходится — благодаря порядку «дети первыми» уже удалённые дети не превращаются в невидимых сирот.

`onUpdate`-каскады работают только для связей на не-PK уникальную колонку (см. [связи](04-schema-model.md)) и распространяются транзитивно: обновление FK-колонки ребёнка, на которую ссылаются внуки, продолжает замыкание. Это касается и `setNull` при **delete**: обнуление FK-колонки ребёнка — это изменение значения, которое видят onUpdate-рёбра внуков — restrict-внук заблокирует удаление, cascade/setNull-внуки последуют за null.

## Truncate

```php
$db->truncate('audit_log');
```

Семантика SQL `TRUNCATE`: все записи удаляются, индексы пересобираются пустыми, автоинкремент сбрасывается в 0 — следующая вставка получит `id = 1` (delete-all, в отличие от truncate, счётчик сохраняет). Foreign-key-действия **не** проверяются (симметрично `dropTable`): висячие FK-значения в детях остаются — если это важно, сначала обработайте детей. Неизвестная таблица → `TABLE_NOT_FOUND`.

## Переименования

Смена имени колонки (`renameColumn`) и таблицы (`renameTable`) — DDL-операции, описаны в [Изменении схемы](12-schema-mutations.md): обе переносят данные, индексы, связи и мету на новое имя и защищены от крашей (для `renameTable` — маркером `_pendingRename`, который дочиняет `repair()`).

## Affected rows

```php
$tbl = $db->table('products');
$tbl->where('discontinued', '=', true)->delete();
echo $tbl->affectedRows();   // число строк последней DML
```

`affectedRows()` равен `0` до первой DML на этом билдере. Read-операции (`select*`, `count`, `exists`, identifier-API) его не меняют.
