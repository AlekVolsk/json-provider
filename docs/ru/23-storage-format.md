# Формат хранения и совместимость версий

У базы на диске есть поколение формата. Поколение 1 — всё, что пишут движки 1.0. Поколение 2 появилось в 1.1. Совместимость двусторонняя: движок 1.0 работает с базой поколения 2, движок 1.1 — с базой поколения 1, и откат библиотеки на 1.0 не требует ручных шагов.

## Манифест формата

Поколение и флаги хранятся в `.jdp/format.json`:

```json
{
    "generation": 2,
    "compat": [],
    "roCompat": [],
    "incompat": []
}
```

У базы поколения 1 манифеста нет — его отсутствие и есть признак поколения 1. `createDatabase()` создаёт базу сразу в поколении 2.

`.jdp/` — dot-каталог, как `.locks/`: валидатор и `repair()` его не видят и не трогают, в архив бэкапа он не попадает. Поэтому движок 1.0, ничего не знающий о манифесте, не считает его сиротой и не удаляет.

Три списка флагов говорят движку, что делать с возможностью формата, которой он не знает:

| Список | Движок, не знающий флага |
| - | - |
| `compat` | игнорирует его |
| `roCompat` | открывает базу только на чтение: любая запись — `StorageReadOnly` |
| `incompat` | отказывается открыть базу: `StorageFeatureUnsupported` |

Поколение выше, чем знает движок, — тоже отказ открыть: `StorageGenerationUnsupported`. Манифест, которому нельзя доверять (не JSON, не объект, поколение ниже 2, список флагов не из непустых строк), — отказ `StorageManifestCorrupt`: угаданное поколение могло бы скрыть флаг, который движку нельзя игнорировать. Незнакомые ключи верхнего уровня читатель пропускает, отсутствующий список флагов равен пустому.

Движок 1.0 манифест не читает вовсе, поэтому всё, что добавляет поколение 2, совместимо с ним по построению, и флагов в поколении 2 нет. Флаги нужны следующим поколениям: версии начиная с 1.1 откажутся работать с форматом, которого не знают, вместо того чтобы прочитать его неверно.

## Штамп таблицы

Полная перезапись таблицы подменяет файл данных переименованием, затем пересобирает индексы, затем коммитит счётчики в мету. Если процесс упал после переименования, а новый файл совпал по размеру со старым (изменилось значение той же длины, например внешний ключ `2 → 4`), проверка только по размеру примет старые индексы за верные. Выборка по индексу пропустит изменённую строку, а `restrict`-проба разрешит удалить родителя, на которого ссылается только она.

Поколение 2 закрывает это окно штампом: каждая полная перезапись записывает в мету, рядом со счётчиками, inode нового файла данных — поле `dataIno`. Переименование меняет inode всегда, даже при том же размере.

Одна проверка доверия обслуживает выборки по индексу, `restrict`-пробы, проверку перед записью, `count()` без условий и валидатор:

| Состояние таблицы | Когда | Индексам доверяем | Что происходит |
| - | - | - | - |
| свежая | размер и inode совпадают со штампом | да | — |
| без штампа | размер совпадает, штампа нет: таблицу создал или восстановил движок 1.0 | да, по размеру, как в 1.0 | предупреждение; штамп появится при следующей полной перезаписи, `repair()` или миграции |
| устаревшая | размер совпадает, inode — нет: файл подменён после последнего коммита со штампом | нет | предупреждение; выборки идут полным сканом, ближайшая запись чинит таблицу канонической перезаписью |
| расхождение | не совпадает размер или нет записи в мете | нет | как в 1.0: полный скан, починка ближайшей записью |

Дозапись inode не меняет, поэтому таблица остаётся свежей — и после `insert` движка 1.0 тоже. Перезапись, сделанная движком 1.0, делает таблицу устаревшей до ближайшей записи нового движка. `renameTable` переносит файлы вместе с inode, штамп остаётся верным.

`validate()` показывает таблицы без штампа и устаревшие как `table_unverified` (info, в `context.freshness` — `unstamped` или `stale`); `repair()` пересобирает их индексы из данных и ставит штамп, не переписывая файл данных. Если в файле есть строки, не являющиеся записями, `repair()` штамп не ставит: индексы их пропустили бы.

В базе поколения 1 штамп не пишется и не проверяется — доверие только по размеру, ровно как в 1.0.

## База поколения 1 на новом движке

Работает так же, как на 1.0: новый движок не пишет ни манифеста, ни штампов. При каждой инициализации провайдера — под PHP-FPM это каждый запрос — пишется предупреждение о том, что база в поколении 1 и защита поколения 2 выключена до миграции.

Предупреждения уходят в PSR-3-логгер провайдера уровнем `warning`. Без логгера — в журнал ошибок PHP через `trigger_error()`:

| Предупреждение | Без логгера |
| - | - |
| база в поколении 1 | `E_USER_DEPRECATED` |
| таблица без штампа или устаревшая (один раз на таблицу на экземпляр провайдера) | `E_USER_DEPRECATED` |
| база открыта только на чтение | `E_USER_WARNING` |

Под нагрузкой база поколения 1 даёт предупреждение на каждый запрос. Это сделано намеренно, чтобы непереведённая база была видна в логах; уберите его [миграцией](07-migrations.md#версионные-миграции).
