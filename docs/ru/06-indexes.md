# Индексы

Индексы ускоряют сортировку и фильтрацию без полного сканирования. Это NDJSON-файлы пар `{key, line}`, отсортированные по ключу; поиск по отсортированным ключам бинарный (O(log n + k)).

## Формат ключа (v2) и маркер `indexFormat`

Ключ — hex-кодированная конкатенация частей, по одной на поле индекса. Часть = тег типа + нагрузка: `null`, `false`, `true` — однобайтовые теги; числа — общий тег и 16 сортируемых байт (int и float одного значения дают **один** ключ: `key(99) === key(99.0)`, `-0.0` сворачивается в `0.0`; за пределами точности double, `|v| > 2^53`, соседние int различаются остаточными байтами, а числовые границы диапазонов сравниваются без остатка — индекс отдаёт надмножество, точность добивает общий дофильтр, результат совпадает с full scan); строки — тег + экранированное содержимое + терминатор, **без обрезки**. Части префиксно-свободны, поэтому составной ключ инъективен: границы компонент не смешиваются. Направление `DESC` инвертирует байты части — порядок ключей соответствует порядку значений в обе стороны. `NAN`/`INF` не индексируемы (`IndexKeyNonFinite`); нефинитное значение в условии запроса деградирует в full scan.

Формат хранится per-table в `meta.json` (`indexFormat`; нет поля — формат 1). Индексы таблицы с форматом ниже текущего не используются: такая таблица читается full scan'ом, а первая же запись (или `rebuildAllIndexes()`, `repairTable()`, `optimizeTable()`) перестраивает все индексы текущим кодировщиком и штампует `indexFormat: 2`. `rebuildIndex()` одного индекса на таблице с форматом 1 перестраивает все индексы: одиночный файл формата 2 под маркером формата 1 отравил бы таблицу. `restore()` после восстановления перестраивает индексы и штампует формат.

## Доверие и деградация

Перед использованием индекса читатель проверяет O(1)-гейт: зафиксированный в мете `byteSize` совпадает с фактическим размером файла данных и `indexFormat >= 2`. Любое сомнение — чужой append, потерянная мета, формат ниже текущего — **тихо** деградирует запрос в full scan (результат корректен, исключения нет); ближайшая запись под table EX чинит и штампует.

Доверенный (v2) индекс читается со структурной валидацией: число записей равно `lineCount`, строки образуют перестановку без дублей и дыр, каждый ключ синтаксически корректен. Нарушение — **громкое** `JsonProviderServiceException`: структурно битый индекс никогда не отдаёт молча неверные строки. Пустой результат индексного поиска авторитетен только после этой валидации. Те же проверки (категория `JsonProviderServiceException`) выполняет `validateTable()`, а `repairTable()` перестраивает и штампует.

## Как выбирается индекс для запроса

`select` выбирает один индекс на вызов, по приоритету:

1. **Ordering-индекс** — если `orderBy()` точно совпадает с полями и направлениями индекса. Записи читаются в порядке индекса, без сортировки в памяти.
2. **Filter-индекс** — если первое поле индекса совпадает с полем первого подходящего условия. Индекс сужает множество строк, читаемых из данных.
3. **Full scan** — если ни один индекс не подходит.

PK-индекс присутствует всегда и естественным образом подхватывается для `WHERE id = N`.

При distinct-выборке индекс даёт только порядок и фильтр: `limit`/`offset` применяются после дедупликации, никогда внутри индексного пути.

В режиме сравнения `Locale` (см. [Билдер запросов](08-query-builder.md)) индекс не используется для сортировки и диапазонов по строковым колонкам — байтовый порядок индекса не совпадает с коллатором; `=`/`IN` по строкам остаются индексируемыми.

## Операторы, которые могут использовать индекс

Через составной индекс исполняются условия только по **первому** полю; условие по второму полю индекс не применяет (корректный результат даёт дофильтрация или full scan). Выборка без `orderBy` возвращает строки в порядке файла независимо от того, использовался ли индекс.

Индексы добавляются и удаляются на живой таблице через `addIndex()`/`dropIndex()` — файл строится из текущих данных до публикации схемы; см. [Изменение схемы](12-schema-mutations.md). Имена с префиксом `_fk_` зарезервированы под служебные FK-индексы движка.

```text
=   ✓  точное совпадение ключа
>   ✓  диапазон от границы вверх
>=  ✓
<   ✓  диапазон до границы
<=  ✓
BETWEEN ✓  (границы-`null` или не-скаляры → full scan)
IN  ✓  (пустой список — авторитетный ноль строк)
LIKE ✗  всегда full scan
NOT *   ✗  всегда full scan
```

## Имена и зарезервированные имена

- Имя индекса `pk` зарезервировано за PK. Объявление обычного индекса с этим именем (без `isPrimary=true`) → `JsonProviderSchemaException`.
- Префикс `_fk_` зарезервирован за служебными FK-индексами движка: `addIndex('_fk_...')` → `ReservedIndexName`.
- Имя файла индекса в схеме **не хранится** — оно вычисляется из имени индекса (`<index-name>.index.ndjson`). Получить его можно через `IndexSchema::getFileName()`.

## Служебные FK-индексы (backing)

Связь с пробующим действием (`cascade`/`restrict` на delete или update) обязана иметь **backing-индекс** — одноколоночный индекс на FK-колонке ребёнка, по которому движок проверяет существование ссылок. Его провизией занимается API связей (`addRelation`):

- если у ребёнка уже есть одноколоночный **пользовательский** индекс на FK-колонке — он переиспользуется (`RelationSchema::backingIndex` = его имя);
- иначе строится **служебный** индекс `_fk_<колонка>` (`isService: true` в схеме). Несколько связей на одну колонку делят один служебный индекс.

Свойства служебных индексов:

- поддерживаются штатной машинерией записи (append/rebuild/repair) как обычные индексы;
- **невидимы планировщику запросов**: select по FK-колонке ведёт себя так, будто колонка не индексирована — служебный индекс существует только для FK-проб;
- их жизненный цикл принадлежит API связей: `dropIndex` служебного имени → `ReservedIndexName`; `dropRelation` удаляет служебный индекс, если его не использует другая пробующая связь (пользовательский backing не трогается);
- `dropIndex` **пользовательского** индекса, служащего backing'ом, не оставляет связь без пробы: тем же изменением схемы достраивается служебная замена, и связь перепривязывается к ней.

FK-пробы проходят тот же конвейер доверия, что и select-путь: O(1)-гейт byteSize+формат (устаревший индекс → честный скан прочитанных строк), затем полная структурная валидация (порча → `JsonProviderServiceException`). Restrict-проба при отсутствующем/непокрывающем backing — громкая ошибка конфигурации `FkBackingIndexMissing`, не тихий скан: у существующих БД её закрывает первый `repair()` (переиспользует покрывающий пользовательский индекс либо достраивает `_fk_<колонка>` и проставляет `backingIndex` — структурная починка, данные не трогаются).

## Объявление индексов при создании таблицы

```php
$db->createTable(TableSchema::create(
    name: 'events',
    columns: ['userId' => 'int', 'createdAt' => 'string'],
    indexes: [
        new IndexSchema(
            name: 'idx_events_user_created',
            fields: [
                new IndexFieldSchema('userId',    SortDirectionEnum::ASC),
                new IndexFieldSchema('createdAt', SortDirectionEnum::DESC),
            ],
        ),
    ],
));
```

Композитный индекс покрывает `orderBy` только когда **все** поля и направления совпадают точно.
