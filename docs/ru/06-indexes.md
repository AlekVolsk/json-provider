# Индексы

Индексы ускоряют сортировку и фильтрацию без полного сканирования. Это NDJSON-файлы пар `{key, line}`, отсортированные по ключу; поиск по отсортированным ключам бинарный (O(log n + k)).

## Формат ключа (v2) и маркер `indexFormat`

Ключ — hex-кодированная конкатенация частей, по одной на поле индекса. Часть = тег типа + нагрузка: `null`, `false`, `true` — однобайтовые теги; числа — общий тег и 16 сортируемых байт (int и float одного значения дают **один** ключ: `key(99) === key(99.0)`, `-0.0` сворачивается в `0.0`; за пределами точности double, `|v| > 2^53`, соседние int различаются остаточными байтами, а числовые границы диапазонов сравниваются без остатка — индекс отдаёт надмножество, точность добивает общий дофильтр, результат совпадает с full scan); строки — тег + экранированное содержимое + терминатор, **без обрезки**. Части префиксно-свободны, поэтому составной ключ инъективен: границы компонент не смешиваются. Направление `DESC` инвертирует байты части — порядок ключей соответствует порядку значений в обе стороны. `NAN`/`INF` не индексируемы (`IndexKeyNonFinite`); нефинитное значение в условии запроса деградирует в full scan.

Формат хранится per-table в `meta.json` (`indexFormat`; нет поля — формат 1). Индексы таблицы с форматом ниже текущего не используются: такая таблица читается full scan'ом, а первая же запись (или `rebuildAllIndexes()`, `repairTable()`, `optimizeTable()`) перестраивает все индексы текущим кодировщиком и штампует `indexFormat: 2`. `rebuildIndex()` одного индекса на таблице с форматом 1 перестраивает все индексы: одиночный файл формата 2 под маркером формата 1 отравил бы таблицу. `restore()` после восстановления перестраивает индексы и штампует формат.

## Доверие и деградация

Перед использованием индекса читатель проверяет O(1)-гейт: зафиксированный в мете `byteSize` совпадает с фактическим размером файла данных и `indexFormat >= 2`. Любое сомнение — чужой append, потерянная мета, формат ниже текущего — **тихо** деградирует запрос в full scan (результат корректен, исключения нет); ближайшая запись под table EX чинит и штампует.

## Как выполняется поиск

Файл индекса после пересборки отсортирован по ключу целиком, дозапись кладёт новые записи в неотсортированный хвост. В базе поколения 2 рядом хранятся производные файлы (см. [формат хранения](23-storage-format.md#производные-файлы)): граница отсортированной головы каждого файла индекса и смещения строк файла данных. С ними поиск файл индекса целиком не читает:

- голова — двоичный поиск прямо по тексту файла: шаг — переход в середину диапазона и одна строка, около log2(n) строк на границу, плюс строки найденного диапазона;
- хвост читается целиком и ищется в памяти; когда в хвосте больше 1024 записей, ближайшая вставка переписывает файл индекса отсортированным;
- найденные строки данных читаются прямым переходом по смещениям, пока нужна не больше чем восьмая часть строк таблицы, иначе — одним проходом по файлу.

Поиск одной строки в таблице на 100 тыс. строк стоит доли миллисекунды и почти не зависит от размера таблицы.

Производные файлы несут inode, размер и метку содержимого файла, который описывают. Не совпало — файл переписала другая версия, процесс упал между записью данных и обновлением, файл подменили, — поиск читает и проверяет файл индекса целиком. Неверных строк устаревший производный файл не даёт. Сортировка по индексу без условий и FK-пробы читают индекс целиком всегда.

## Проверки при поиске

Индекс, прочитанный целиком, проверяется весь: число записей равно `lineCount`, строки образуют перестановку без дублей и дыр, каждый ключ синтаксически корректен.

Поиск по голове проверяет то, что прочитал: каждая прочитанная запись — пара `{key, line}` с корректным ключом и номером строки внутри файла данных; ключи на пути поиска идут по порядку; голова и хвост вместе содержат ровно `lineCount` записей; ни одна строка данных не найдена дважды; ключ, вычисленный из каждой возвращённой строки, совпадает с ключом записи индекса, которая на неё указала. Порча вне пути поиска — повреждённая запись далеко от искомого ключа — таким поиском не видна, её находят `validate()` и `validateTable()`, которые читают файл индекса целиком.

Любое нарушение — **громкое** `JsonProviderServiceException`: структурно битый индекс не отдаёт молча неверные строки. Те же полные проверки выполняет `validateTable()`, а `repairTable()` перестраивает и штампует.

## Как выбирается индекс для запроса

`select` выбирает один индекс на вызов, по приоритету:

1. **Ordering-индекс** — если `orderBy()` точно совпадает с полями и направлениями индекса. Записи читаются в порядке индекса, без сортировки в памяти.
2. **Filter-индекс.** Если условия `=` фиксируют ведущие поля индекса подряд и вместе с диапазоном (`>`, `>=`, `<`, `<=`, `BETWEEN`) по следующему полю покрывают два поля или больше, берётся индекс, у которого так покрыто больше всего полей, при равенстве — объявленный раньше. Иначе — первый индекс, у которого первое поле совпадает с полем первого подходящего условия. Индекс сужает множество строк, читаемых из данных.
3. **Full scan** — если ни один индекс не подходит.

PK-индекс присутствует всегда и естественным образом подхватывается для `WHERE id = N`.

При distinct-выборке индекс даёт только порядок и фильтр: `limit`/`offset` применяются после дедупликации, никогда внутри индексного пути.

В режиме сравнения `Locale` (см. [Билдер запросов](08-query-builder.md)) индекс не используется для сортировки и диапазонов по строковым колонкам — байтовый порядок индекса не совпадает с коллатором; `=`/`IN` по строкам остаются индексируемыми.

## Проверка unique при вставке

`insert` проверяет unique-ограничение через индекс, если у таблицы есть пользовательский индекс ровно на полях ограничения — в любом порядке и с любыми направлениями: равенство полного ключа означает равенство каждого поля. Связь вычисляется по совпадению полей и нигде не хранится. Служебные `_fk_`-индексы не учитываются: движок создаёт и удаляет их вместе со связями. Индексы под ограничения автоматически не создаются.

Поиск идёт по отсортированной голове и хвосту, как для запроса, и с теми же проверками (см. «Проверки при поиске»). Найденные записи сравниваются типострогим ключом ограничения (см. [семантику unique-ограничений](04-schema-model.md#семантика-unique-ограничений)): ключ индекса сливает `1` и `1.0`, поэтому может только расширить список кандидатов, но не сузить его. Значение, которое есть в данных, но не в индексе из-за порчи вне пути поиска, такой проверке не видно — как и запросу; пропущенный из-за такой порчи дубль `validate()` покажет находкой `unique_duplicate` рядом с находкой о повреждённом индексе.

Нет подходящего индекса или не записана голова файла индекса (база поколения 1, устаревший производный файл) — `insert` читает всю таблицу, один раз на все такие ограничения. Запись с `null` в любом поле ограничения в проверке не участвует и ничего не читает. `update` и `importRecords` перезаписывают таблицу и проверяют уникальность по всему итоговому набору — индекс им не нужен.

Без индекса цена вставки растёт с размером таблицы: её всю читают и разбирают. С индексом на тех же полях вставка почти не отличается от вставки в таблицу без unique. Сам индекс стоит дозаписи с `fsync` в свой файл на каждой вставке и перестройки при перезаписях, поэтому на маленькой таблице полное чтение может обойтись дешевле. `validate()` отмечает ограничение без индекса находкой `unique_index_missing` уровня `info`.

## Операторы, которые могут использовать индекс

Составной индекс ищет по префиксу ключа: значения `=` по ведущим полям подряд и, если есть, диапазон по следующему полю — один отрезок файла индекса. Условия по полям после префикса, в том числе `IN` и `LIKE`, индекс не применяет — их проверяет дофильтрация; `IN` работает только по первому полю. Выборка без `orderBy` возвращает строки в порядке файла независимо от того, использовался ли индекс.

Индексы добавляются и удаляются на живой таблице через `addIndex()`/`dropIndex()` — файл строится из текущих данных до публикации схемы; см. [Изменение схемы](12-schema-mutations.md). Имена с префиксом `_fk_` зарезервированы под служебные FK-индексы движка.

```text
=   ✓  точное совпадение ключа
>   ✓  диапазон от границы вверх
>=  ✓
<   ✓  диапазон до границы
<=  ✓
BETWEEN ✓  (границы-`null` или не-скаляры → full scan)
IN  ✓  (пустой список — авторитетный ноль строк)
LIKE ✗  всегда full scan
NOT *   ✗  всегда full scan
```

## Имена и зарезервированные имена

- Имя индекса `pk` зарезервировано за PK. Объявление обычного индекса с этим именем (без `isPrimary=true`) → `JsonProviderSchemaException`.
- Префикс `_fk_` зарезервирован за служебными FK-индексами движка: `addIndex('_fk_...')` → `ReservedIndexName`.
- Имя файла индекса в схеме **не хранится** — оно вычисляется из имени индекса (`<index-name>.index.ndjson`). Получить его можно через `IndexSchema::getFileName()`.

## Служебные FK-индексы (backing)

Связь с пробующим действием (`cascade`/`restrict` на delete или update) обязана иметь **backing-индекс** — индекс, первое поле которого — FK-колонка ребёнка; по нему движок проверяет существование ссылок. Проба сравнивает только первую часть ключа, поэтому остальные поля индекса на ответ не влияют. Его провизией занимается API связей (`addRelation`):

- если у ребёнка уже есть одноколоночный **пользовательский** индекс на FK-колонке — он переиспользуется (`RelationSchema::backingIndex` = его имя);
- при `setFkBackingPolicy(FkBackingPolicyEnum::LeadingColumn)` переиспользуется и пользовательский индекс, у которого FK-колонка — первое поле (одноколоночный по-прежнему в приоритете). На таблице на один индекс меньше, каждая вставка дописывает на один файл меньше; FK-проба читает файл индекса целиком и на составном индексе чуть дороже. По умолчанию (`SingleColumn`) берётся только одноколоночный. Версии до 1.2 такую связь считают непокрытой — перед откатом см. [Версионные миграции](07-migrations.md#11--12);
- иначе строится **служебный** индекс `_fk_<колонка>` (`isService: true` в схеме). Несколько связей на одну колонку делят один служебный индекс.

Свойства служебных индексов:

- поддерживаются штатной машинерией записи (append/rebuild/repair) как обычные индексы;
- **используются планировщиком запросов** наравне с пользовательскими: select по FK-колонке идёт через служебный индекс. Индекс живёт, пока жива связь: после `dropRelation` (если индекс не нужен другой пробующей связи) выборки по колонке молча возвращаются к полному просмотру. Колонке, по которой выборки нужны независимо от связи, объявите пользовательский индекс до связи — `addRelation` переиспользует его как backing;
- их жизненный цикл принадлежит API связей: `dropIndex` служебного имени → `ReservedIndexName`; `dropRelation` удаляет служебный индекс, если его не использует другая пробующая связь (пользовательский backing не трогается);
- `dropIndex` **пользовательского** индекса, служащего backing'ом, не оставляет связь без пробы: тем же изменением схемы связь перепривязывается к замене — при `LeadingColumn` к другому подходящему пользовательскому индексу, если он есть, иначе к достроенному служебному.

FK-пробы проходят тот же конвейер доверия, что и select-путь: O(1)-гейт byteSize+формат (устаревший индекс → честный скан прочитанных строк), затем полная структурная валидация (порча → `JsonProviderServiceException`). Restrict-проба при отсутствующем/непокрывающем backing — громкая ошибка конфигурации `FkBackingIndexMissing`, не тихий скан: у существующих БД её закрывает первый `repair()` (переиспользует покрывающий пользовательский индекс либо достраивает `_fk_<колонка>` и проставляет `backingIndex` — структурная починка, данные не трогаются).

## Объявление индексов при создании таблицы

```php
$db->createTable(TableSchema::create(
    name: 'events',
    columns: ['userId' => 'int', 'createdAt' => 'string'],
    indexes: [
        new IndexSchema(
            name: 'idx_events_user_created',
            fields: [
                new IndexFieldSchema('userId',    SortDirectionEnum::ASC),
                new IndexFieldSchema('createdAt', SortDirectionEnum::DESC),
            ],
        ),
    ],
));
```

Композитный индекс покрывает `orderBy` только когда **все** поля и направления совпадают точно.
