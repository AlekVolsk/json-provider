# Резервное копирование и восстановление

Провайдер умеет экспортировать текущее состояние данных в один `.tar.gz` и восстанавливать обратно. Никаких внешних утилит и composer-пакетов — используются встроенные расширения `ext-phar` и `ext-zlib`.

## Backup

```php
$archivePath = $db->backup('/var/backups');
// например /var/backups/backup-2026-04-27_173045.tar.gz

$archivePath = $db->backup('/var/backups/snapshot.tar.gz');
// явный путь
```

Поведение:

- если `$destination` — каталог, имя файла генерируется с таймстампом;
- если в нём нет расширения `.tar.gz`/`.tar` — добавляется `.tar.gz`;
- если итоговый путь уже занят → `BACKUP_ARCHIVE_EXISTS`;
- если итоговый путь — внутри каталога БД → `BACKUP_DESTINATION_INSIDE_DB` (бэкап там сразу станет orphan-ом для валидатора целостности);
- сохраняются только схема и данные таблиц — мета и индексы выводятся из данных и пересоздаются при restore.

Раскладка архива:

```text
manifest.json                 # {format, version, createdAt, tables}
information_schema.json
tables/<table>.ndjson
```

## Restore

```php
$db->restore('/var/backups/snapshot.tar.gz');
```

Поведение:

1. валидация архива (формат manifest, версия manifest, набор таблиц совпадает с текущей схемой);
2. снятие safety-snapshot текущего состояния БД во временный архив;
3. для каждой таблицы: чтение записей из архива, нормализация по текущей схеме, сортировка по `id`, запись файла данных, пересоздание индексов, пересчёт меты;
4. при успехе — удаление safety-snapshot;
5. при ошибке — rollback из safety-snapshot, исключение `RESTORE_FAILED`. Если упал и rollback — оба сообщения плюс путь к snapshot присутствуют в сообщении исключения, чтобы можно было восстановиться вручную.

Набор таблиц в архиве должен **точно совпадать** со схемой — лишние/недостающие таблицы → `BACKUP_SCHEMA_MISMATCH`. Наборы колонок в самих записях совпадать не обязаны: пропущенные колонки заполняются `null`, лишние — отбрасываются.
