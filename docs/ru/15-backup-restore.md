# Резервное копирование и восстановление

Провайдер умеет экспортировать текущее состояние данных в один `.tar.gz` и восстанавливать обратно. Никаких внешних утилит и composer-пакетов — используются встроенные расширения `ext-phar` и `ext-zlib`.

## Backup

```php
$archivePath = $db->backup('/var/backups');
$archivePath = $db->backup('/var/backups/snapshot.tar.gz');
// явный путь
```

Поведение:

- если `$destination` — каталог, имя файла генерируется с таймстампом;
- если в нём нет расширения `.tar.gz`/`.tar` — добавляется `.tar.gz`;
- если итоговый путь уже занят → `BackupArchiveExists`;
- если каталога назначения нет или в него нельзя писать → `BackupDestinationNotWritable`;
- если запись архива сорвалась (например, ext-phar не принимает путь с `.phar` в имени каталога) → `BackupWriteFailed` с причиной; временные файлы удалены, по целевому пути ничего не остаётся, повторный backup туда же не блокируется;
- если итоговый путь — внутри каталога БД → `BackupDestinationInsideDb` (бэкап там сразу станет orphan-ом для валидатора целостности);
- перед экспортом база проходит проверку целостности под тем же локом: любая находка уровня `error` и выше (нет файла данных, битый индекс, недоделанный `renameTable`) → `BackupSourceInvalid`, архив не создаётся — сначала `validate()`/`repair()`. Находки уровня `warning` (дубли unique, FK-сироты) экспорт не блокируют: архив сохраняет данные как есть;
- сохраняются только схема и данные таблиц — мета и индексы выводятся из данных и пересоздаются при restore.

Экспорт целиком выполняется **под эксклюзивным локом всей БД**: ни один писатель не находится в полёте, все таблицы снимаются из одного зафиксированного поколения — межтабличный каскад (`cascade`/`setNull`) не может попасть в архив полупримененным, висячих FK между таблицами архива не бывает. Лок держится и на время компрессии. В архив попадают только объявленные схемой файлы — временные `*.tmp` не включаются никогда.

Раскладка архива:

```text
manifest.json                 # {format, version, createdAt, tables, counters, checksums}
information_schema.json
tables/<table>.ndjson
```

Манифест несёт два поля валидации (версия формата остаётся `1`, поля опциональны):

- `counters` — `таблица → lastInsertedId` на момент экспорта, снимается из меты, а **не** выводится из данных: удалённый верхний id после restore не будет выдан повторно;
- `checksums` — `имя члена архива → sha256` его байтов, посчитанный из тех же байтов, что легли в архив. Сам `manifest.json` чек-суммой не покрыт: подмена манифеста **вместе** с описанными им членами остаётся необнаружимой — если это критично, храните архивы под внешним контуром целостности (подпись, immutable-хранилище).

## Restore

```php
$db->restore('/var/backups/snapshot.tar.gz');
```

Поведение:

1. валидация архива: формат и версия манифеста, затем **sha256-проверка каждого члена**, для которого манифест знает чек-сумму, — несовпадение даёт `BackupChecksumMismatch`, и к БД никто не притрагивается. Архив без `counters`/`checksums` (поля манифеста опциональны) восстанавливается без проверки;
2. сверка набора таблиц с текущей схемой (в дефолтном режиме — см. adopt ниже);
3. под db EX + EX-локами всех затронутых таблиц: снятие safety-snapshot текущего состояния БД во временный архив — `<temp>/jp-snapshot-<hex>/snapshot.tar.gz`, где `<temp>` — `sys_get_temp_dir()`, а каталог создаётся с правами `0700` (вложенный экспорт переиспользует уже удерживаемый лок и проверку целостности пропускает — восстановление битой базы и есть назначение restore);
4. для каждой таблицы: чтение записей из архива, нормализация по схеме, сортировка по `id`, запись файла данных, пересоздание индексов со штампом формата v2, восстановление `lastInsertedId = max(счётчик манифеста, max(id))` — у архива без `counters` остаётся только `max(id)`; затем зачистка необъявленных файлов подкаталога таблицы (осиротевшие индексы снесённых индексов, брошенные `*.tmp`) — после restore `validate()` чист по `orphan_index_file`;
5. при успехе — удаление safety-snapshot;
6. при ошибке — rollback из safety-snapshot (схема, данные и счётчики берутся из снапшота, включая счётчики из **его** манифеста), исключение `JsonProviderServiceException`. Если упал и rollback — оба сообщения плюс путь к snapshot присутствуют в сообщении исключения, чтобы можно было восстановиться вручную.

Restore сериализуется со всеми писателями: конкурентные insert/update либо целиком завершаются до снапшота, либо начинаются после восстановления.

### Режим по умолчанию: данные архива в текущую схему

Режим по умолчанию восстанавливает **только данные** и раскладывает их по **текущей** схеме базы — сама схема не меняется. Это инструмент для работы с конкретной базой: вы знаете, что восстанавливаете и во что, и доводите результат сами. Полное восстановление — схема вместе с данными — это режим adopt, см. ниже.

Что делается:

- набор таблиц в архиве должен **точно совпадать** со схемой — лишние/недостающие таблицы → `JsonProviderServiceException`;
- записи раскладываются по колонкам текущей схемы: присутствующее значение пишется **как есть**, лишние ключи отбрасываются, пропущенные колонки заполняются дефолтом типа (`''`/`0`/`0.0`/`false`, `null` — для nullable; отсутствующая not-null temporal-колонка дефолта не имеет и роняет restore громко);
- непарсимые строки архива пропускаются с `warning` в PSR-3-логгер (если он задан);
- записи сортируются по `id`, индексы пересобираются, счётчик `lastInsertedId` восстанавливается, необъявленные файлы подкаталога таблицы удаляются.

Чего **не** делается — значения не прогоняются через валидацию записи:

- тип значения не сверяется с типом колонки: строка из архива ляжет в `int`-колонку, дата в неканоническом виде — в `datetime`-колонку;
- вложенный массив или объект в значении заменяется на `null`;
- unique-ограничения и связи не проверяются.

После restore в этом режиме приведите данные к схеме сами:

- `validate()` покажет дубли unique, `null` в not-null колонках и висячие FK;
- **несоответствие типов `validate()` не видит** — его проверяйте и исправляйте по своим данным (выборкой через `selectAllByArray()` и правкой через `updateByArray()` или миграцией);
- после ручных правок в обход провайдера — `rebuildAllIndexes()` / `repair()`.

## Временные файлы

Backup и restore работают через временные файлы: промежуточные `.jp-backup-<hex>.tar`/`.tar.gz` в каталоге назначения бэкапа, приватная копия восстанавливаемого архива `<temp>/jp-restore-<hex>.tar.gz` (права `0600`) и safety-snapshot. Все они удаляются при любом исходе — успехе, исключении и фатальной ошибке PHP (исчерпание памяти, `max_execution_time`): уборку в последнем случае выполняет shutdown-обработчик.

Единственное исключение — **safety-snapshot, когда он остаётся единственной копией состояния до restore**:

- **упал rollback** — путь к снапшоту есть в сообщении исключения `RestoreRollbackFailed`;
- **restore прерван фатальной ошибкой** — база может остаться частично восстановленной; путь к снапшоту пишется в PSR-3-логгер уровнем `critical`, а без логгера — в PHP error log, рядом с самой фатальной ошибкой.

В обоих случаях восстановитесь из снапшота обычным `restore()`, затем удалите его каталог `jp-snapshot-<hex>` вручную.

Ограничения:

- `kill -9` и падение процесса не дают выполниться никакой уборке — в `<temp>` могут остаться каталоги `jp-snapshot-*` и файлы `jp-restore-*`, в каталоге назначения — `.jp-backup-*`;
- shutdown-обработчики PHP выполняются по порядку регистрации: если прикладной обработчик, зарегистрированный раньше, сам падает фатально, до уборки провайдера дело не доходит;
- `<temp>` у php-fpm может оказаться не системным `/tmp`: при `PrivateTmp=true` в systemd-юните у сервиса свой каталог (из шелла — `/tmp/systemd-private-*-<сервис>/tmp`), он стирается при рестарте сервиса; `sys_temp_dir` в php.ini и переменная `TMPDIR` тоже меняют расположение. Оставленный снапшот ищите по пути из лога или исключения, а не в `/tmp` наугад.

## Восстановление со схемой архива (adopt)

```php
$db->restore($archive, adoptArchivedSchema: true);
$db->restore($archive, adoptArchivedSchema: true, pruneExtraTables: true);
```

С `adoptArchivedSchema: true` архивная `information_schema.json` **заменяет** текущую схему — это полное восстановление: схема и данные приходят из архива вместе, путь восстановления в пустую БД и путь отката структурных изменений. Данные ложатся в ту схему, с которой были сохранены, поэтому расхождения данных со схемой, описанные для режима по умолчанию, здесь не возникают. С `pruneExtraTables: true` база приводится к архиву целиком:

- архивная схема прогоняется через те же строгие загрузчики, что и живая: имена таблиц/колонок (защита от path traversal — имя `..` отвергается), закрытый список типов, строгий парс связей. Невалидная схема → исключение до любых мутаций; подмену схемы ловит её чек-сумма ещё раньше;
- таблицы архива, отсутствующие в текущей БД, создаются с нуля (файл данных, индексы, мета);
- таблицы текущей БД, отсутствующие в архиве, **по умолчанию блокируют restore** (`JsonProviderServiceException` с подсказкой) — данные не удаляются молча; с `pruneExtraTables: true` они удаляются вместе с файлами и метой;
- откат при ошибке восстанавливает и прежнюю схему: rollback повторно «адоптирует» схему снапшота.
