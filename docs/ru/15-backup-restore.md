# Резервное копирование и восстановление

Провайдер умеет экспортировать текущее состояние данных в один `.tar.gz` и восстанавливать обратно. Никаких внешних утилит и composer-пакетов — используются встроенные расширения `ext-phar` и `ext-zlib`.

## Backup

```php
$archivePath = $db->backup('/var/backups');
$archivePath = $db->backup('/var/backups/snapshot.tar.gz');
// явный путь
```

Поведение:

- если `$destination` — каталог, имя файла генерируется с таймстампом;
- если в нём нет расширения `.tar.gz`/`.tar` — добавляется `.tar.gz`;
- если итоговый путь уже занят → `BackupArchiveExists`;
- если итоговый путь — внутри каталога БД → `BackupDestinationInsideDb` (бэкап там сразу станет orphan-ом для валидатора целостности);
- сохраняются только схема и данные таблиц — мета и индексы выводятся из данных и пересоздаются при restore.

Экспорт целиком выполняется **под эксклюзивным локом всей БД**: ни один писатель не находится в полёте, все таблицы снимаются из одного зафиксированного поколения — межтабличный каскад (`cascade`/`setNull`) не может попасть в архив полупримененным, висячих FK между таблицами архива не бывает. Лок держится и на время компрессии. В архив попадают только объявленные схемой файлы — временные `*.tmp` не включаются никогда.

Раскладка архива:

```text
manifest.json                 # {format, version, createdAt, tables, counters, checksums}
information_schema.json
tables/<table>.ndjson
```

Манифест несёт два поля валидации (версия формата остаётся `1`, поля опциональны):

- `counters` — `таблица → lastInsertedId` на момент экспорта, снимается из меты, а **не** выводится из данных: удалённый верхний id после restore не будет выдан повторно;
- `checksums` — `имя члена архива → sha256` его байтов, посчитанный из тех же байтов, что легли в архив. Сам `manifest.json` чек-суммой не покрыт: подмена манифеста **вместе** с описанными им членами остаётся необнаружимой — если это критично, храните архивы под внешним контуром целостности (подпись, immutable-хранилище).

## Restore

```php
$db->restore('/var/backups/snapshot.tar.gz');
```

Поведение:

1. валидация архива: формат и версия манифеста, затем **sha256-проверка каждого члена**, для которого манифест знает чек-сумму, — несовпадение даёт `BackupChecksumMismatch`, и к БД никто не притрагивается. Legacy-архив (без `counters`/`checksums`) восстанавливается без проверки;
2. сверка набора таблиц с текущей схемой (в дефолтном режиме — см. adopt ниже);
3. под db EX + EX-локами всех затронутых таблиц: снятие safety-snapshot текущего состояния БД во временный архив (вложенный экспорт переиспользует уже удерживаемый лок);
4. для каждой таблицы: чтение записей из архива, нормализация по схеме, сортировка по `id`, запись файла данных, пересоздание индексов со штампом формата v2, восстановление `lastInsertedId = max(счётчик манифеста, max(id))` — у legacy-архива остаётся только `max(id)`; затем зачистка необъявленных файлов подкаталога таблицы (осиротевшие индексы снесённых индексов, брошенные `*.tmp`) — после restore `validate()` чист по `orphan_index_file`;
5. при успехе — удаление safety-snapshot;
6. при ошибке — rollback из safety-snapshot (схема, данные и счётчики берутся из снапшота, включая счётчики из **его** манифеста), исключение `JsonProviderServiceException`. Если упал и rollback — оба сообщения плюс путь к snapshot присутствуют в сообщении исключения, чтобы можно было восстановиться вручную.

Restore сериализуется со всеми писателями: конкурентные insert/update либо целиком завершаются до снапшота, либо начинаются после восстановления.

В дефолтном режиме набор таблиц в архиве должен **точно совпадать** со схемой — лишние/недостающие таблицы → `JsonProviderServiceException`. Наборы колонок в самих записях совпадать не обязаны: пропущенные колонки заполняются дефолтом типа (`''`/`0`/`0.0`/`false`, `null` — для nullable; отсутствующая not-null temporal-колонка дефолта не имеет и роняет restore громко), лишние — отбрасываются. Непарсимые строки архива пропускаются с `warning` в PSR-3-логгер (если он задан).

## Восстановление со схемой архива (adopt)

```php
$db->restore($archive, adoptArchivedSchema: true);
$db->restore($archive, adoptArchivedSchema: true, pruneExtraTables: true);
```

С `adoptArchivedSchema: true` архивная `information_schema.json` **заменяет** текущую схему — это путь восстановления в пустую БД и путь отката структурных изменений:

- архивная схема прогоняется через те же строгие загрузчики, что и живая: имена таблиц/колонок (защита от path traversal — имя `..` отвергается), закрытый список типов, строгий парс связей. Невалидная схема → исключение до любых мутаций; подмену схемы ловит её чек-сумма ещё раньше;
- таблицы архива, отсутствующие в текущей БД, создаются с нуля (файл данных, индексы, мета);
- таблицы текущей БД, отсутствующие в архиве, **по умолчанию блокируют restore** (`JsonProviderServiceException` с подсказкой) — данные не удаляются молча; с `pruneExtraTables: true` они удаляются вместе с файлами и метой;
- откат при ошибке восстанавливает и прежнюю схему: rollback повторно «адоптирует» схему снапшота.
