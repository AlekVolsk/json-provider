# Изменение схемы — reorder, migrate, индексы, unique, rename, drop

Структуру уже существующей таблицы можно менять дальше: колонки — `migrateColumns`/`reorderColumns`/`renameColumn`, индексы — `addIndex`/`dropIndex`, unique-ограничения — `addUniqueConstraint`/`dropUniqueConstraint`, имя таблицы — `renameTable`, плюс несколько read-only-хелперов, чтобы посмотреть, что зарегистрировано.

Все DDL-операции выполняются под эксклюзивной блокировкой базы и затронутых таблиц и первым шагом перечитывают схему с диска — конкурентные изменения схемы из других процессов не теряются, а гонка одноимённого `createTable` честно завершается `TABLE_ALREADY_EXISTS` у проигравшего.

`createTable` работает в порядке «схема → мета → файлы»: файлы данных и индексов создаются последними и заводятся «начисто» (мусор от упавшего удаления с тем же именем в новую таблицу не протекает). Краш посреди операции оставляет зарегистрированную таблицу без меты/файлов — это окно самолечится первой же записью в таблицу либо явным `repairTable()`.

## reorderColumns

`reorderColumns()` меняет порядок колонок существующей таблицы. Перезапишет и схему, и каждую запись, чтобы они согласованно следовали новому порядку.

```php
$db->table('products')->reorderColumns(['name', 'price', 'category_id']);
```

Поведение:

- неизвестные колонки в `$newOrder` → `REORDER_COLUMNS_UNKNOWN`;
- дубликаты колонок → `REORDER_COLUMNS_DUPLICATE`;
- если `id` нет в `$newOrder` — он автоматически дописывается в начало;
- если `id` есть, но не первый — перемещается на 0-ю позицию;
- после нормализации id список обязан содержать каждую существующую колонку, иначе → `REORDER_COLUMNS_INCOMPLETE`;
- индексы пересобираются штатной полной перезаписью (writeAll), их логическое содержимое не меняется — порядок ключей в записи не влияет на ключи индекса; заодно штампуется актуальный `indexFormat`.

Сначала обновляется схема, потом перезаписываются записи. Если второй шаг упадёт, порядок записей будет восстановлен следующей мутацией или явным вызовом `repairTable()`.

## migrateColumns — добавить / удалить / переупорядочить колонки

`migrateColumns()` приводит **колонки** существующей таблицы к целевой `TableSchema`: за один проход добавляет, удаляет и переупорядочивает колонки и перезаписывает файл данных. Операция — только про колонки: индексы, unique-ограничения и комментарии таблицы остаются какими были; `indexes`/`uniqueConstraints`, переданные в целевой схеме, игнорируются — структуры индексов и ключей меняются только через `addIndex`/`dropIndex`/`addUniqueConstraint`/`dropUniqueConstraint`. Возвращает списки добавленных и удалённых колонок.

```php
$result = $db->migrateColumns(TableSchema::create(
    name: 'users',
    columns: [
        'email' => ColumnTypes::STRING,
        'name'  => ColumnTypes::STRING,
        'phone' => ColumnTypes::STRING_NULLABLE,  // новая колонка
        // 'isActive' удаляется тем, что её нет в списке
    ],
));
// $result === ['added' => ['phone'], 'dropped' => ['isActive']]
```

Что делает:

- **добавляет** колонки, которые есть в целевой схеме, но не хранятся — существующие строки получают дефолт по типу: `''`, `0`, `0.0`, `false` или `null` для nullable-типа (единый источник дефолтов — `Schema\ColumnDefaults`);
- **удаляет** колонки, которые есть в таблице, но не в целевой схеме — их значения вычищаются из каждой строки (комментарий удалённой колонки уходит вместе с ней);
- **переупорядочивает** колонки под целевую схему.

Это no-op (возвращает пустые `added`/`dropped`), когда набор и порядок колонок уже совпадают.

Проверки — каждая бросает `StorageException` и ничего не пишет:

- таблицы не существует → `TABLE_NOT_FOUND`;
- у удерживаемой колонки меняется тип → `MIGRATE_COLUMN_TYPE_CHANGE`. `migrateColumns` никогда не переэнкодит хранимые значения, поэтому смена типа (в том числе перевод колонки в nullable) вне его контракта — см. рецепт ниже;
- в **непустую** таблицу добавляется not-null-колонка без нулевого дефолта (`date` / `time` / `datetime`, `year` / `month` / `day`) → `MIGRATE_COLUMN_NO_DEFAULT`. Объявите её nullable либо добавьте, пока таблица ещё пуста;
- существующее unique-ограничение или индекс таблицы ссылается на удаляемую колонку → `MIGRATE_FIELD_UNKNOWN_COLUMN` — сначала снимите индекс/ограничение (`dropIndex`/`dropUniqueConstraint`).

Крашебезопасность: весь мигрированный набор записей **энкодится в буфер до** любой мутации — неэнкодируемое хранимое значение (чужие байты в файле) прерывает операцию с нетронутым диском (`INVALID_RECORD`). Затем публикуется схема и только потом перезаписываются данные (temp+fsync+rename), пересобираются индексы, коммитится мета и обновляется кэш. Краш между схемой и данными дочиняется `repair()` в **целевое** состояние: добавленные not-null-колонки добиваются дефолтами типа, не `null`.

### Смена типа колонки — рецепт

Смена типа не реализована ни одной мутацией (громкий `MIGRATE_COLUMN_TYPE_CHANGE`). Путь: добавить новую nullable-колонку нужного типа → перелить значения `update`-ами → удалить старую колонку (`dropIndex`/`dropUniqueConstraint` при необходимости, затем `migrateColumns`) → `renameColumn` новой колонки в старое имя.

## renameColumn — переименовать колонку

`renameColumn()` переименовывает колонку целиком: ключ в схеме (та же позиция и тип), поля индексов и unique-ограничений, комментарий колонки, стороны связей (`foreignKey` дочерней стороны и `references` родительской) и сами данные. Привязанный DTO перекомпилируется под новую схему; если DTO продолжает ссылаться на старое имя — привязка снимается, и объектные чтения падают громким `DTO_NOT_REGISTERED` вместо тихо сломанной гидрации.

```php
$db->renameColumn('users', 'phone', 'phone_number');
```

Гварды (ничего не пишется): колонки нет → `COLUMN_NOT_FOUND`; `id` переименовать нельзя → `PK_CONTRACT_VIOLATED`; новое имя невалидно → `INVALID_COLUMN_NAME`; занято → `COLUMN_ALREADY_EXISTS`.

Краш-модель как у `migrateColumns` (схема раньше данных) с одной оговоркой: `repair()` после краша сходится к **новой** схеме, добивая переименованную колонку дефолтом типа, а не перенося старые значения, — если данные в колонке важны, сделайте бэкап перед переименованием.

## addIndex / dropIndex — индексы

`addIndex()` добавляет вторичный индекс и строит его файл из текущих данных; `dropIndex()` убирает индекс из схемы и удаляет файл. Обе — под EX-локами базы и таблицы.

```php
$db->addIndex('users', new IndexSchema(
    'idx_users_email',
    [new IndexFieldSchema('email', SortDirectionEnum::ASC)],
));
$db->dropIndex('users', 'idx_users_email');
```

- имя занято → `INDEX_ALREADY_EXISTS`; поле не в колонках → `MIGRATE_FIELD_UNKNOWN_COLUMN`; PK-индекс добавить/удалить нельзя → `PK_CONTRACT_VIOLATED`; неизвестное имя при dropIndex → `INDEX_NOT_FOUND`;
- `addIndex`: сначала файл и построение, схема публикуется последней — краш между ними оставляет необъявленный файл, который `validate()` видит как orphan и `repair()` удаляет. На таблице legacy-формата все индексы пересобираются текущим кодеком и штампуется `indexFormat=2`;
- `dropIndex`: сначала схема, потом файл — краш между ними оставляет orphan-файл с той же судьбой.

## addUniqueConstraint / dropUniqueConstraint — unique-ограничения

`addUniqueConstraint()` перед публикацией пре-чекает существующие данные (типострогие ключи, SQL-семантика NULL: записи с `null` в поле ключа не участвуют): хранящийся дубликат → `UNIQUE_VIOLATION`, схема не меняется. `dropUniqueConstraint()` снимает ограничение (schema-only).

```php
$db->addUniqueConstraint('users', new UniqueConstraint('uq_users_email', ['email']));
$db->dropUniqueConstraint('users', 'uq_users_email');
```

Имя занято → `UNIQUE_CONSTRAINT_ALREADY_EXISTS`; поле не в колонках → `MIGRATE_FIELD_UNKNOWN_COLUMN`; неизвестное имя при drop → `UNIQUE_CONSTRAINT_NOT_FOUND`.

## renameTable — переименовать таблицу

`renameTable()` переносит на новое имя ключ схемы, все связи, ссылающиеся на таблицу, запись меты (счётчик и размеры сохраняются) и физику — каталог и файл данных; файлы индексов не переименовываются (они названы по имени индекса). Локи — база EX плюс EX на **оба** имени.

```php
$db->renameTable('users', 'accounts');
```

Гварды: `$from` не существует → `TABLE_NOT_FOUND`; `$to` невалидно → `INVALID_TABLE_NAME`; `$to` занято в схеме, в мете или на диске → `TABLE_ALREADY_EXISTS`.

Краш-модель: первым в `meta.json` пишется маркер `_pendingRename` `{from, to}`, затем атомарно (одна RMW-транзакция) коммитится схема со связями, затем мета и файловая система, последним снимается маркер. Оставшийся маркер `repair()` сверяет **по фактическому состоянию схемы**: схема уже на новом имени — мета и физика докатываются под него; схема ещё на старом — переименование не состоялось, снимается только маркер. `validate()` репортит маркер как `rename_incomplete` (error).

## dropTable — удалить таблицу

`dropTable()` полностью удаляет таблицу: запись в схеме (со всеми relations, где она участвует), запись в мете, файлы и привязанный DTO-маппинг. Идемпотентен — неизвестная таблица это no-op.

```php
$db->dropTable('audit_log');
```

Замечания:

- операция выполняется под эксклюзивными блокировками базы и таблицы; запись в схеме удаляется первой (схема → мета → файлы), поэтому инвариант «у каждой зарегистрированной таблицы есть запись в мете» не нарушается посреди операции;
- внешние ключи **не** проверяются: удаление родительской таблицы молча снимает её relations и оставляет в детях FK-колонки/значения висячими (как SQL `DROP TABLE`, а не `DROP TABLE ... RESTRICT`). Если это важно — сначала удалите или мигрируйте детей.

## Интроспекция

Read-only-хелперы, чтобы посмотреть, что зарегистрировано, — удобно при написании идемпотентных миграций:

```php
$db->hasTable('users');       // bool — зарегистрирована ли таблица?
$db->tableNames();            // list<string> — имена всех зарегистрированных таблиц
$db->columnNames('users');    // list<string> — колонки в порядке схемы (id первым)
```
