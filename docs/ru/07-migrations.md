# Миграции — определение схемы и версионные миграции

## Определение схемы

Провайдер вызывается из ваших собственных миграций, и изменение структуры — создание таблиц — лишь один из их видов. Раннера миграций в комплекте нет: как их отслеживать и чем запускать (CLI-командой, шагом деплоя, бутстрапом первого запроса) — решает сам проект. Ниже — форма такой структурной миграции.

Тонкий класс доступа отдаёт общий экземпляр `JsonDataProvider`, создавая хранилище при первом обращении:

```php
use AV\JsonProvider\JsonDataProvider;

final class Db
{
    private static JsonDataProvider | null $instance = null;

    public static function provider(): JsonDataProvider
    {
        if (self::$instance === null) {
            $path = '/var/data/myapp';
            self::$instance = JsonDataProvider::exists($path)
                ? JsonDataProvider::getInstance($path)
                : JsonDataProvider::createDatabase($path);
        }

        return self::$instance;
    }
}
```

Миграция объявляет структуру — две таблицы. Дополнительные ключи (unique-ограничение и индекс) — только у `users`; `posts` обходится одним первичным ключом:

```php
use AV\JsonProvider\Query\SortDirectionEnum;
use AV\JsonProvider\Schema\ColumnTypes;
use AV\JsonProvider\Schema\IndexFieldSchema;
use AV\JsonProvider\Schema\IndexSchema;
use AV\JsonProvider\Schema\TableSchema;
use AV\JsonProvider\Schema\UniqueConstraint;

final class InitialMigration
{
    /** @return list<TableSchema> */
    public function tables(): array
    {
        return [
            TableSchema::create(
                name: 'users',
                columns: [
                    'email'    => ColumnTypes::STRING,
                    'name'     => ColumnTypes::STRING,
                    'isActive' => ColumnTypes::BOOL,
                ],
                uniqueConstraints: [
                    new UniqueConstraint('uq_users_email', ['email']),
                ],
                indexes: [
                    new IndexSchema('idx_users_email', [new IndexFieldSchema('email', SortDirectionEnum::ASC)]),
                ],
                tableComment: 'Учётные записи пользователей',
                columnComment: [
                    'email'    => 'Адрес электронной почты, уникальный',
                    'name'     => 'Отображаемое имя',
                    'isActive' => 'Активна ли учётная запись',
                ],
            ),
            TableSchema::create(
                name: 'posts',
                columns: [
                    'userId' => ColumnTypes::INT,
                    'title'  => ColumnTypes::STRING,
                    'body'   => ColumnTypes::STRING_NULLABLE,
                ],
                tableComment: 'Публикации пользователей',
                columnComment: [
                    'userId' => 'Автор публикации (users.id)',
                    'title'  => 'Заголовок',
                    'body'   => 'Тело публикации (необязательно)',
                ],
            ),
        ];
    }
}
```

Прогон миграции — это обход её шагов, и здесь важна развилка по обработке сбоя.

**Падать на первом же сбое** уместно, когда шаги зависят друг от друга и частичное применение недопустимо: исключение пробрасывается и обрывает весь прогон.

```php
$db = Db::provider();

foreach ((new InitialMigration())->tables() as $schema) {
    $db->createTable($schema);   // любой сбой прерывает весь прогон
}
```

**Пропускать сбойный шаг с логированием** уместно, когда шаги независимы: незачем ронять создание остальных таблиц из-за одной. Ошибку ловим, пишем в лог и продолжаем; а `TableAlreadyExists` заодно делает повторный прогон идемпотентным.

```php
use AV\JsonProvider\Exception\JsonProviderException;
use AV\JsonProvider\Exception\Locale\JsonProviderErrorEn;

$db = Db::provider();

foreach ((new InitialMigration())->tables() as $schema) {
    try {
        $db->createTable($schema);
    } catch (JsonProviderException $e) {
        if ($e->error === JsonProviderErrorEn::TableAlreadyExists) {
            continue;   // уже применено — повторный прогон безопасен
        }

        error_log("миграция: таблица «{$schema->name}» пропущена — " . $e->getMessage());
    }
}
```

Поздние миграции редко просто создают таблицы. Как изменить или удалить существующую — добавить/удалить/переупорядочить колонки или снести таблицу целиком — см. [Изменение схемы](12-schema-mutations.md); `hasTable()` / `columnNames()` помогают делать такие шаги идемпотентными, а `diffTable()` показывает, что отделяет таблицу от желаемой схемы.

## Версионные миграции

Новая версия библиотеки может принести новое поколение формата хранения (см. [Формат хранения](23-storage-format.md)). Версионная миграция не трогает ни ваших данных, ни вашей схемы: она приводит к поколению движка служебную часть базы — манифест формата, штампы таблиц, индексы. Запускается явно, один раз на базу.

### Статус и миграция

```php
$status = $db->storageStatus();

if (!$status->isCurrent()) {
    $report = $db->migrateStorage();
}
```

`storageStatus()` только читает и блокировок на запись не берёт. Он сообщает:

- поколение базы и поколение движка (`generation`, `engineGeneration`);
- флаги манифеста (`compat`, `roCompat`, `incompat`) и признак `readOnly`;
- шаги, которые выполнит миграция (`pendingSteps`, например `['1->2']`);
- таблицы, которые она пересоберёт и проштампует или которым построит производные файлы (`pendingTables`);
- флаги `compat` поколения движка, которых в манифесте ещё нет (`pendingFeatures`).

Статус читает диск, а не память экземпляра, поэтому видит миграцию, выполненную другим процессом.

`migrateStorage(?int $toGeneration = null)` доводит базу до поколения движка (или до указанного, не выше него) и делает свежими все таблицы:

- выполняется под EX-локом базы и EX-локами всех таблиц, как `repair()`, — это операция для выкладки, а не для живого трафика; по цене она равна `rebuildAllIndexes()` по всей базе;
- поколения проходятся по шагу за раз (`1->2`, в будущем `2->3` и так далее); каждый шаг идемпотентен, манифест пишется последним действием шага. Краш посреди шага оставляет базу в предыдущем поколении, повторный запуск доделывает шаг;
- таблица, в файле данных которой есть строки, не являющиеся записями, не трогается вовсе: перезапись потеряла бы такую строку, а индексам, построенным в обход неё, нельзя доверять. Она попадает в `skippedTables` отчёта и продолжает работать как раньше. Исключение — оборванный неподтверждённый хвост от упавшей дозаписи: починка его отбрасывает, как и при обычной записи;
- миграция идёт только вверх: цель ниже поколения базы или выше поколения движка — `StorageMigrationTargetInvalid`. Для базы, уже находящейся в поколении движка, `migrateStorage()` делает свежими таблицы без штампа и устаревшие.

`MigrationReport` возвращает `fromGeneration`, `toGeneration`, `steps`, `refreshedTables` и `skippedTables`.

Восстановление из архива заканчивается той же миграцией, поэтому `restore()` архива любой версии оставляет базу в поколении движка.

### Порядок обновления

1. **До выкладки проверьте данные.** Запустите `validate()` и разберите находки `broken_record`: таблицу со строками, не являющимися записями, миграция пропустит.
2. **Выложите код.** Пока выкладка идёт, старые и новые процессы могут работать одновременно — обе версии берут одни и те же блокировки. До миграции каждая инициализация провайдера пишет предупреждение о том, что база в старом поколении (PSR-3 `warning`, без логгера — `E_USER_DEPRECATED`); под PHP-FPM это предупреждение на каждый запрос.
3. **Один раз выполните миграцию** из сценария выкладки, в тихий момент — код выше.
4. **Перезапустите долгоживущие процессы** (CLI-воркеры, демоны очередей): манифест читается один раз на экземпляр провайдера, и до перезапуска такой процесс ведёт себя как движок предыдущего поколения. Для совместимых поколений это безопасно; будущий шаг к несовместимому поколению потребует остановить все процессы, работающие с базой, до миграции.

### Откат и смешанная выкладка

Откат с 1.1 на 1.0 ручных шагов не требует. Движок 1.0 не видит `.jdp/`, игнорирует поле `dataIno` в мете и сохраняет его при своих коммитах, архивы 1.1 восстанавливает как обычные (см. [резервное копирование](15-backup-restore.md)). После возврата на 1.1 таблицы, которые 1.0 успела переписать, окажутся устаревшими и починятся ближайшей записью, `repair()` или миграцией.

Пока рядом работают процессы 1.0, переписанные ими таблицы обслуживаются полным сканом до ближайшей записи 1.1.

### 1.0 → 1.1: поколение 1 → 2

База 1.0 работает на 1.1 так же, как на 1.0; защита поколения 2 — штамп таблиц — включается после миграции. Шаг `1->2` не принимает индексы 1.0 на веру:

- таблица без штампа получает индексы, пересобранные из данных, и штамп — файл данных не переписывается;
- таблица с расходящимися счётчиками чинится канонической перезаписью;
- таблица, чей штамп ещё совпадает, не трогается.

Последним действием шаг пишет манифест `.jdp/format.json` поколения 2.

### 1.1 → 1.2

Поколение не меняется. Версия 1.2 ведёт в `.jdp/` производные файлы для индексного поиска (см. [формат хранения](23-storage-format.md#производные-файлы)) и отмечает это флагами `compat` `lineOffsets` и `sortedIndexHeads`. База от 1.1 работает на 1.2 сразу: таблица получает файлы при первой записи, а до того поиск по ней идёт прежним путём. `storageStatus()` перечисляет такие таблицы в `pendingTables` и недостающие флаги в `pendingFeatures`; `migrateStorage()` строит файлы всем таблицам — смещения строк из файла данных, отсортированный файл индекса там, где у него нет записанной головы, — и дописывает флаги в манифест. Данные и индексы при этом не меняются.

У блокировок базы и таблиц в 1.2 есть турникет — пустые файлы `gate.<файл блокировки>` в `.locks/` (см. [конкурентность](18-concurrency.md#ограничения)). Взаимоисключение держат сами файлы блокировок, поэтому 1.2 работает рядом с 1.1 и 1.0; читатели старых версий за ждущим писателем 1.2 не встают. После отката файлы турникетов остаются в `.locks/` и ничему не мешают.

Откат на 1.1 или 1.0 ручных шагов не требует: эти версии производных файлов не видят и флаги `compat` пропускают. После возврата на 1.2 таблицы, которые старый движок переписал, ищутся прежним путём до ближайшей записи; `migrateStorage()` строит их файлы сразу.

Исключение — связи, которые при `FkBackingPolicyEnum::LeadingColumn` сели на составной индекс (см. [Индексы](06-indexes.md#служебные-fk-индексы-backing)). 1.1 и 1.0 считают такую связь непокрытой: `delete` по `restrict` падает на `FkBackingIndexMissing`, `cascade` и `setNull` читают таблицу ребёнка целиком. После отката запустите `repair()`: он построит служебный индекс и перепривяжет связь к нему.
